# 项目功能导航

导航采用两层结构：[docs/feature-map.yaml](../../../docs/feature-map.yaml) 为唯一总索引，[docs/features/](../../../docs/features/) 存放按功能拆分的 Markdown 文档。从 worktree 工作时使用该 worktree 的文件。导航记录“功能在哪里实现、下一步读什么”，不复制实现细节或充当完整产品规格。

## 查找实现

1. 先读 YAML 索引的覆盖说明，按用户描述、页面名、路由、协议名或符号匹配 `features` 中的 `name` 和 `keywords`，只读取命中项的 `doc`。不要默认加载整个 `docs/features/`；索引变大时可用 `rg -n` 定位相关条目。
2. 按条目的“入口 → 关键实现 → 验证入口”阅读当前源码，确认调用、导入和状态归属。feature map 和记忆都只是线索；与源码冲突时以当前源码为准，不能仅凭路径存在就认定功能已接入或可用。
3. 未命中或专题未覆盖所查功能时，继续使用搜索、脚本或其他工具查找实现并完成原任务；不要将导航缺失当作功能不存在或停止工作的理由。先在相关页面或领域目录搜索，再按需扩大范围，只追踪当前任务所需的调用链。
4. 完成原任务后、最终答复前，将本次查找中已从源码确认但导航未记录的功能补入 feature map；即使任务只是定位、解释、排错或审查，没有业务代码变更，也执行这一步。用户明确要求不修改任何文件或不更新导航时，只在结论中报告缺漏，不写文件。

## 随工作维护

交付前，对照本次查找结果及实际变更检查功能导航：

- 查找补录：优先补充已有专题的实现入口与职责；确属独立功能时再创建专题并加入 YAML 索引。如果只是关键词未命中已有记录，补充 name 或 keywords，不重复建专题。按实际覆盖同步调整 scope、not_yet_mapped 或专题内的待补充范围，局部补录不代表整个领域已覆盖。
- 新增功能：已有专题能容纳时补充该文档；独立功能则创建 `docs/features/<feature-id>.md` 并加入 YAML 索引。至少记录可搜索的功能名、实现入口和关键文件职责。
- 功能变动：更新受影响的行为范围、调用链、状态或协议定位点；只写已从代码确认的信息。
- 重构、移动或重命名：同时检查 YAML 的 `doc`、`entrypoints` 及专题文档，替换旧路径和符号，检查其他文档对旧位置的交叉引用；同步调整职责拆分。
- 删除功能：移除失效的索引和条目；若仍有调用方或替代入口，按当前代码说明保留范围或新位置，不凭单个文件删除推断整项功能消失。
- 仅内部细节、样式或文案变化，且现有条目仍准确：无需制造导航 diff，也不更新无关条目的核对日期。

只补录本次任务实际查到并核对的范围，不为完善导航额外扫描全仓。仅发现文件名或搜索片段时，先确认调用关系和职责再补录；尚未确认的部分明确保留为待核对，不编造成已实现功能。已有未提交实现可作为当前工作区证据，但需标注条目依赖该改动，不把它说成已提交的架构。保留其他人的文档修改；不把未验证的记忆、计划或猜测写成现状。

## 条目约定

YAML 保持轻量，只负责路由到文档和首读代码：

- `path_base: repository-root`：`doc` 和 `entrypoints` 均为仓库相对路径，不相对 YAML 文件解析。
- `features` 中每项包含唯一的 `id`（小写连字符命名）、`name`、`keywords`、`doc` 和少量 `entrypoints`。`doc` 指向 `docs/features/<id>.md`，入口选最有助于开始阅读的实现文件，不枚举全部依赖。
- `scope` 说明整体覆盖边界，`not_yet_mapped` 保留尚未建立专题的范围。已建专题的内部缺口写在专题内，不在索引重复详细职责、核对日期或调用链。

功能文档保存具体导航信息：

- 功能名称、覆盖范围和返回 `../feature-map.yaml` 的链接；路由、协议名或关键符号按定位需要补充。专题名称不代表已实现同名独立页面。
- 覆盖状态与最近核对日期：区分“已核对入口/主链路”和“仅发现入口、内部待补充”，不声称整体已验证。
- 入口及关键实现：Markdown 链接相对当前专题文档解析，例如 `../../src/main.tsx`，链接文字写仓库相对路径；每个文件附简短职责。其他专题通过同目录文件名链接，不再使用单文件小节锚点。优先具体实现文件，目录只用于仍待细分的范围。
- 有助于定位时补充简短调用链、状态归属或跨模块边界；不复制全部 API 字段、枚举、文件树或代码。
- 已存在且相关的测试或 Story 入口；没有核对则明确略过，不为填充导航新增测试。

不记录容易漂移的行号、测试通过数量、会话流水账或凭据。新增专题参考现有文档，不需要固定数量的实现文件或小节。跨功能的实现允许被多个专题引用，但职责细节尽量由一个专题维护，其他专题通过链接引导阅读。

## 完成检查

解析 YAML，确认功能 id 唯一、`doc` 与 `entrypoints` 存在，各专题可从索引到达，Markdown 链接有效。确认本次新增或调整的关键符号和职责与源码一致；移动或删除时搜索旧路径残留。对文档执行适当的格式和 diff 检查即可，不因导航维护扩大业务测试范围。交付时说明补充了哪些范围和仍未覆盖什么；文件存在性或格式检查不等于功能运行验收。
